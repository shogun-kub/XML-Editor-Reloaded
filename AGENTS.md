# Инструкции для ИИ-ассистентов — XML Editor Reloaded

Этот файл содержит правила, контекст и архитектурные ограничения для ИИ-ассистентов, работающих над проектом.

## 📌 Контекст проекта

- **Название**: XML Editor Reloaded.
- **Назначение**: десктопное приложение для просмотра и редактирования XML-таблиц (TableData) мода Jagged Alliance 2 1.13 для игры Jagged Alliance 2. Дополнительно — просмотр изображений предметов в формате STI.
- **Стек**: .NET 10, C#, WPF (GUI), SQLite (метаданные таблиц).
- **Архитектура**: backend — отдельные библиотеки классов (XML-парсинг, работа с метаданными, декодирование изображений и т. п.); frontend — WPF-приложение.
- **Решение**: папка `xml-editor-reloaded/` в корне репозитория. Все создаваемые и изменяемые проекты должны находиться внутри неё.
- **Справочные проекты**: `References/` — сторонние исходники, библиотеки и данные игры, предназначенные только для изучения. Подробное описание — в `REFERENCE-PROJECTS-STRUCTURE.md`.
- **Версии данных**: полные сборки мода `References/JA 2 1.13 v4` и `References/JA 2 1.13 v5`. Редактор должен корректно работать с обеими, а также с будущими версиями, где набор полей может меняться. Таблицы: `<GameDir>\Data-1.13\TableData`; изображения: `Data-1.13\BigItems`, `Data-1.13\Interface`, `Data-1.13\tilesets\0`.
- **Локализация данных**: v4 — русская сборка (25 файлов-оверлеев `Russian.*`), v5 — английская базовая сборка без оверлеев. Это штатное состояние, а не пропущенные файлы.
- **Устройство решения**: см. `PROJECT-STRUCTURE.md`. При изменении структуры решения обновляйте этот документ.

## 🌍 Общие правила

- **Язык общения**: Русский.
- **Кодировка файлов**: Всегда используйте UTF-8 без BOM.
- **Стиль работы**: Предпочтительны минимальные, точечные правки. Избегайте массового переписывания или рефакторинга файлов, если об этом не просили напрямую.
- **Автономность**: При возникновении ошибок компиляции или сборки ИИ должен пытаться самостоятельно их исправить до того, как запрашивать помощь у пользователя. Доводите задачу до рабочей сборки.

- `References/JA 2 1.13 Image viewer`, `References/xml-editor`, `References/JA_2_1.13_TableData_Editor`, `References/FreeImage`, `References/JA 2 1.13 v4` и `References/JA 2 1.13 v5` можно читать и анализировать без отдельного разрешения. Изменять их по-прежнему нельзя.

- Не подключайте файлы из `References/` как проектные ссылки, ресурсы или источник данных времени выполнения. Копируйте нужные алгоритмы, метаданные и тестовые образцы в проект.

## 🛡 Целостность XML-данных

Главное правило: **редактор не имеет права ломать XML-файлы**.

- Никогда не удаляйте элементы, поля или колонки из XML-таблиц. Это относится и к полям, которых нет в метаданных, DTO или модели: их нужно сохранять без изменений.
- Не приводите записи к фиксированному набору колонок. Записи разрежены: в `Items.xml` разные элементы содержат разный набор полей (сотни различных наборов на файл). Отсутствующие в записи элементы должны остаться отсутствующими, присутствующие — присутствовать.
- Сохраняйте лексическое представление и тип значения: целые (`0`, `-1`), дробные (`1.3`, `0.0`, `-0.2`), строки, пустые элементы. Не преобразовывайте `1.0` в `1`, не меняйте регистр и не используйте культуру текущей ОС при записи чисел — только invariant culture.
- Сохраняйте порядок элементов, повторяющиеся элементы, регистр имён и XML-декларацию. Сохранять исходные BOM и переводы строк необязательно: в v4 встречаются файлы и с CRLF, и с LF, с BOM и без него.
- Изменяйте только те значения, которые пользователь явно отредактировал. Не пересобирайте документ сериализатором целиком.
- Неизвестные элементы и атрибуты сохраняйте для обратного round-trip.
- Загрузка → сохранение без правок не должна менять содержимое файла. Если содержимое не изменялось — файл не перезаписывается вообще.
- Ошибки в XML (например, лишний закрывающий тег в `v5/TableData/Lookup/AttachmentPoint.xml`) показывайте пользователю. Не исправляйте и не перезаписывайте файл автоматически.
- Валидация должна предупреждать, а не удалять или нормализовать данные.
- Метаданные и модель должны быть версионно-независимыми: не хардкодьте поля под v4 или v5. Новые поля, появившиеся в другой версии, должны сохраняться и отображаться, даже если для них ещё нет описания.

## 🌐 Локализация

- **v4 — русская локализация, v5 — английская базовая версия.** Отсутствие файлов `Russian.*` в v5 — норма, а не ошибка или потеря данных.
- Файлы локализации — это **оверлеи** с префиксом языка: `<Language>.<BaseFile>.xml` в той же папке `TableData` (например, `Russian.Items.xml`, `Russian.Cities.xml`). Они не являются самостоятельными таблицами и не должны попадать в список таблиц как отдельные сущности.
- Оверлей содержит ключ записи (`uiIndex`, `mIndex`, `pIndex`, `ubIndex`, `uiSlotIndex`, `SectorGrid`) и только переопределённые поля. Оверлей может быть неполным: в v4 `Russian.Items.xml` содержит 1742 записи из 1776, `Russian.Backgrounds.xml` — 316 из 357.
- При отображении базовая таблица является источником схемы и значений по умолчанию. Оверлей накладывается по ключу; отсутствующее в оверлее поле показывается из базовой таблицы с пометкой «не переведено».
- При сохранении правка перевода пишется только в оверлей и только в затронутое поле. Базовая таблица не изменяется. Структурные/непереводимые поля, которые уже есть в оверлее (`Enabled`, `Sector`, `popup`, `generator`), сохраняются как есть.
- Оверлеи подчиняются тем же правилам целостности XML: не удалять поля, сохранять порядок элементов. BOM и переводы строк сохранять необязательно; в v4 у оверлеев встречаются и CRLF, и LF, BOM есть только у 4 из 25 файлов.
- Не создавайте оверлей копированием всей базовой таблицы. В новый оверлей попадают только ключ и переводимые поля (плюс необходимые структурные элементы).
- Вложенные структуры требуют отдельных ключей: `CITY_INFO/CITYLIST/CITY` — по `uiIndex`; `FACILITYTYPES/FACILITYTYPE/ASSIGNMENT` — по `ubAssignmentType`; `MERCGEARLIST/MERCGEAR/GEARKIT` — по порядковому номеру набора.
- Валидация локализации должна показывать отчёт о недостающих переводах, «сиротских» ключах, дубликатах и пустых значениях. Не заполняйте переводы автоматически.
- **Локализация самого редактора**: все строки UI — в RESX-ресурсах, без хардкода. Минимум английский и русский языки; переключение языка — через настройки.

## 🏗 Архитектурные правила

- Backend-библиотеки не должны ссылаться на WPF-сборки и не должны знать о GUI. Зависимость направлена только от frontend к backend.
- Парсинг и сохранение XML, доступ к метаданным таблиц, декодирование STI и работа с изображениями выполняются в backend-библиотеках.
- Изображения в backend представляются как сырые пиксельные данные (например, RGBA-буфер); преобразование в `BitmapSource` и отображение — задача WPF-слоя.
- Длительные операции (загрузка таблиц, декодирование изображений, сохранение) не должны блокировать UI-поток. Используйте асинхронные методы, `CancellationToken` и отмену операций.
- При сохранении XML-таблиц сохраняйте структуру документа, порядок элементов, регистр имён и исходную кодировку. Не переформатируйте файлы игры без необходимости.
- Изменяйте только те файлы игры, которые пользователь явно открыл и сохранил. Настройки приложения храните отдельно от папки `TableData` (каталог приложения или `%AppData%`).
- Метаданные таблиц хранятся в SQLite. Схема метаданных должна быть версионируемой и не должна требовать ручного редактирования пользователем.
- Логика загрузки и сохранения управляется метаданными, а не отдельными ветками кода для v4/v5. Отличия версий — это данные, а не отдельные реализации.

## 💻 Стиль кода

- Все файлы исходного кода C# — строго UTF-8 без BOM.
- Предпочтительно MVVM: бизнес-логика и работа с данными не размещаются в code-behind WPF-окон.
- Не используйте блокирующие вызовы (`.Result`, `.Wait()`) в UI-потоке.
- Публичные типы и члены backend-библиотек должны иметь XML-документацию.
- Не оставляйте закомментированный код и отладочные выводы в завершённой работе.

## 📝 XML-комментарии (Документация)

- Должны быть подробными и строго на английском языке.
- Обязательно описывайте параметры (`<param>`) и структуру возвращаемых данных (`<returns>`), а также исключения (`<exception>`), если они предусмотрены контрактом.
- Если метод возвращает стандартный результат API, опишите поля `error_code`, `error_text` и `data`.
- Удаляйте системные или сгенерированные ИИ префиксы из имён (например, не начинайте описание со слова "Метод").
- Не допускайте дублирования блоков `<summary>`.
