- **M2 metadata layer:** two embedded migrations — `0001_InitialSchema.sql` and `0002_PrototypeSeed.sql` (seeded with a throwaway Python script straight from the prototype SQLite, not a committed tool). Seed holds 73 tables (53 prototype + 20 overlay-carrying tables whose key field was read from the real v4 XML), 76 key segments, 12 list fields, 3 dict fields, 61 translatable paths, language `ru → Russian`. `DatabaseMigrator` is embedded-resource driven (`Metadata.Migrations.*.sql`, version from the filename prefix), transactional, idempotent, and refuses a database whose schema is newer (`metadata.downgrade_unsupported`). Tables also store `RecordElement`, so metadata fully describes root + record element.
- **M2 findings:** real v4 has **238** base tables and 25 overlays; v5 has **239** base tables and 0 overlays. The catalogue separates overlays by the language prefix taken from the `Languages` table, and marks `IsMapped` only when a metadata provider is supplied.
- **Schema tables:** `SchemaMigrations`, `Tables`, `TableKeys`, `Columns`, `ListFields`, `DictFields`, `Languages`, `TranslatableFields` (later migrations add `ColumnHints`, `FlagLookupMappings`, `TableRelations`, `RecordKeyFields`, `ClassVisibilityRules`).
- **M6 validation (commit `85d6c1b`):** `Core.Validation.ValidationCodes` + `Xml.Validation.TableValidator.ValidateAsync(document, lookupRepository, languageCode, ct)` — read-only. Unknown field → `Info`; invalid type, missing lookup reference, duplicate/missing primary key, malformed dict mask (must have exactly one `%Index%`; non-numeric index) → `Warning`; an unmapped table returns a single `Info` `validation.unmapped`. **The seed initially had no `Columns` rows**, so type/lookup/unknown-field checks only fire for tables given column metadata; on the real v4/v5 corpus only key and dict-mask checks were active until M14.5.
- **Validation gap (historical):** `TableValidator` reads only `metadata.Columns` and does not look at `ColumnHints`, and the seed has no `Columns` rows — so on real data type/lookup/unknown-field checks were effectively inactive.
- **Columns seeding M14.5 (2026-10-24, user asked whether it was forgotten):** critical path was M14 → M14.5 → M15 because M15 cannot build lookup editors without `LookupTable`/types. Scope: a one-off generator reads `References/xml-editor/BackEnd/DatabaseCode.vb` (read-only) and emits an embedded migration `0005_*.sql`; every field is validated against v4 **and** v5 (declared type parses, lookup file + ID exist, field is present) before acceptance; discrepancies are reported and curated by hand. Policy: `ColumnHints` stays the main non-declaring layer for present fields; `Columns` only where declaring absent fields is deliberate (lookup/config tables) or behind an explicit "declaring" flag; `Items.Items` stays on hints to keep sparse semantics. Validator uses hints for present fields, enables unknown-field checks only with a verified field set, and treats masks/`ULong` (`usItemClass` up to `1073741824`) as `Flags`/`uint` without `int` overflow. Tests: 224 `Items` fields typed with lookups, v4/v5 corpus free of false warnings, lookup IDs resolve, seed never writes XML.
- **M14.5 audit findings (2026-10-24, before the milestone):** confirmed against the code — `Columns` had 0 seeded rows, `ColumnHints` existed **only for `Items.Items`** (224 rows, migration `0004`), and `TableValidator` never consulted hints, so type/lookup validation was inactive on real data. Two blocking facts:
  - **`LookupEntry` was `int`-based** (`Core/Abstractions/ILookupRepository.cs`: `record LookupEntry(int Id, string Name)`), but real lookups hold 64-bit IDs — v5 `Lookup/ItemFlag.xml` has `id` `8589934592` (also `4294967296`) and `ItemClass` up to `1073741824`, so `ItemFlag` failed to load. Widening the ID to `long`/`ulong` was a prerequisite for seeding and M15 lookup editors. Real item flag maxima in v5: `usItemClass` 1073741824, `AttachmentClass` 33554432, `usActionItemFlag` 32768 — `uint` suffices for `Items`, but the width choice should be re-verified.
  - **Legacy lookups are often not `Lookup/*.xml`.** `MakeColumn`'s lookup args frequently name main tables (`"ITEM","uiIndex","szLongItemName"`, `"AMMO","uiIndex","AmmoCaliber"`) plus a SQL-ish filter (`"usItemClass <> 1 OR uiIndex=0"`) and `ReferenceRequired`; only 20 legacy tables come from `MakeLookupTable` (23 `Lookup/*.xml`). Legacy `MakeColumn` signature order: name, caption, type, defaultValue, lookup table/value/text column, addBlank, filter, hideInGrid, maxLength, lookup sort, tooltip, ReferenceRequired, FirstValuePrefix, sourceColumn. The policy decision (extend metadata with value/text column + filter and teach the lookup repository to read main tables, vs import only real XLOOKUP files and report the rest) was open — do not invent synthetic lookup files.
  - **Legacy vs real column counts:** `MakeItemsTable` 257, `MakeWeaponsTable` 50, `MakeAttachmentTable` 4 vs 224 items fields present in real data; every discrepancy must be explained (stale/computed/localized) rather than silently dropped.
  - **Recommended order for M14.5:** inventory `DatabaseCode.vb` → verify every `(table, field)` candidate against v4/v5 (present, type parses, lookup file+ID exist) with a discrepancy report → decide `Columns`-vs-`ColumnHints` policy and the lookups-not-in-`Lookup/*.xml` question → widen lookup IDs/flag width → generate `0005_*.sql` → make `TableValidator` resolve `Columns` then hints for present fields → tests/corpora → docs + `M14.5:` commit. Do not generate SQL before the verification pass, or stale fields become false warnings and broken lookup editors.
- **M15 lookup/Boolean/flag editors (2026-10-24):** migration `0006_FlagLookupMappings.sql` attaches a `LookupTable` to 11 flag fields that already have a verified `Flags` hint (`usItemClass`/`pRestriction` → `Lookup.ItemClass`, `AttachmentClass`, `nasAttachmentClass`, `nasLayoutClass`, `AttachmentPoint`/`AvailableAttachmentPoint`, `DrugType`, `ammoflag`); hints stay non-declaring, types unchanged. `usActionItemFlag` has no lookup file and stays unnamed. `App/ViewModels/LookupColumnData` loads lookup names per column in the active language, keeps unknown IDs as raw with an `(unknown)` marker, and falls back to a text column with a `⚠` header warning when the lookup file is malformed (v5 `Lookup/AttachmentPoint.xml`). Grid: `DataGridTemplateColumn` combos for lookup columns, checkboxes for Boolean that never turn an absent field into `0` without a user action; details panel mirrors this. `BitEditorViewModel` accepts bit names from lookup masks (only power-of-two IDs) and shows the exact name of composite values. Limits: combos only for 15 Lookup fields in 10 tables; no arbitrary ID entry; composite lookup entries are not split into bits; main-table lookups still missing.
- **M23b2 metadata (2026-10-25, commits `296a98d`/`eec9a4f`/`e68e2f3`):** migration `0011` corrects `CompatibleFaceItems` ChildRows/Reverse direction, adds `LabelKey` to the reverse `Attachments`/`Launchables` relations, and seeds two direction-qualified `ClassVisibilityRules` (`Items.Attachments|attachmentIndex` = 268484606, `Items.Launchables|itemIndex` = 16). Migration `0012` adds exact `ItemCapacityPerSize0..34` integer hints (35), bringing `ColumnHints` to 1958. Migration `0013` adds `SymmetricKeyPairs` (2 rows) for `Items.IncompatibleAttachments` (`itemIndex`/`incompatibleattachmentIndex`) and `Items.CompatibleFaceItems` (`compatiblefaceitemIndex`/`itemIndex`); `TableMetadata.SymmetricKeyPair` exposes it. Totals: 13 migrations, 25 class-visibility rules, 1020 relations, 173 tables.
- **M23b3 metadata (2026-10-25, commit `83f37f7`):** migration `0014` creates `LookupValues` (`LookupName`, `Value`, `DisplayName`, `Ordinal`) with 24 fixed `Lookup.SkillTrait` rows and adds three `TableRelations` flags/columns: `IncludeKeyZero`, `NoneValue`, `NoneDisplay`. It converts the three robot skill hints to `Lookup`/`LookupCombo`, seeds 22 relations (7 weapon sound fields, 2 explosion sound fields, `Explosives.ubAnimationID`, 12 LBE pocket fields), and marks the 8 filtered merc gear slots `IncludeKeyZero=1`. Sound relations use `RecordFields.RecordKey` (`#Key`, zero-based positional key) and the virtual `Text` display field; `AltExplosionSoundID` uses `NoneValue=-1`/`NoneDisplay='None'`. `ITableMetadataProvider.GetLookupValuesAsync` serves file-less lookups. Totals: 14 migrations, 1042 relations, 173 tables, 1958 hints, 24 fixed lookup values. Known data anomaly: item 1761 has 505 in both burst-sound fields while `BurstSounds` has 128 rows.
- **M23b4 metadata (2026-10-25, commit `M23b4: validation limits and 64-bit masks`):** migration `0015` adds nullable `ColumnHints.Minimum`/`Maximum` (inclusive INTEGER, validation-only) and seeds 123 bounded fields: Items.Items 61, Items.Weapons 14, Items.Explosives 8, Items.Magazines 1, Items.LoadBearingEquipment 4, Inventory.MercStartingGear 35. Bounds come from the legacy designer spinners; `ItemSize` is 0..99 (MAX_ITEM_SIZE default; 120 records are exactly 99), `mSmall0/1Quantity` are 0..100 while other quantities are 0..10, prices are -32000..32000 and -1..32000. Two legacy limits that contradict the data are deliberately not seeded (`PercentStatusDrainReduction`, `usOverheatingDamageThreshold`); `ubGraphicNum`, `nasLayoutClass`, `uiIndex` and the 33 nested stance controls are excluded (M23b5). New tables: `ExclusiveFlagGroups` (one `launcher_type` group: Cannon/Mortar/GrenadeLauncher/RocketLauncher) and `ClassValueLimits` (LBE `lbeClass` 0→0, 1→5, 2→12, 3→7, 4→12 over `lbePocketIndex%Index%`, max-ordinal semantics because 39 records/version have holes). Bounds live in `ColumnHints` because bounded fields are non-declaring everywhere (`Columns` holds only lookup `id`/`name`). Seed uses grouped `UPDATE … WHERE XmlFieldName IN (…) AND TableId = (SELECT …)`; `UPDATE … FROM` cannot see the target table in this SQLite dialect. Totals: 15 migrations, 1042 relations, 173 tables, 1958 hints (123 with bounds), 1 exclusive group, 5 class limits.
- **Why this order:** M2 had to come before M5 because overlays need real keys and translatable paths; the M14.5 audit notes above were superseded by the verified seed, but the 64-bit lookup widening and the main-table-lookup policy remain the reasons not to invent synthetic lookup files.
