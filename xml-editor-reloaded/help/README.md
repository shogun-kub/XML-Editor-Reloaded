# TableData field help

This folder documents the XML tables under `TableData` for the JA2 1.13 mod. The help is
written for modders and for the editor's future context help; it explains what a table is,
what every field means, which values are valid, and where the behaviour is implemented.

The documentation is **English-first**. Terms come from the C++ source and the XML files, so
the text does not go through a Russian translation before it is reviewed. A Russian edition
is a separate later step (`help/ru/`), built from the reviewed English originals and governed
by `GLOSSARY.md`.

## Scope

- Base tables from `References/JA 2 1.13 v4` and `v5` (the union of both versions).
- Every leaf field, including nested paths and repeating containers.
- Lookup tables, including the repaired `AttachmentPoint` file in v5.
- Cross-version differences and localization overlays.
- Multi-stage formulas kept in their own chapters: `FORMULAS.md`.
- Explicit unknowns; no invented meanings.

Language overlays (`Russian.*.xml`) are not separate tables. They are described in
`Localization.md`; a table page lists only its translatable fields.

## Source hierarchy

1. Game loader/save code - behaviour, types, defaults, limits.
2. XML comments and readme files - author intent, enums, ranges (check against code).
3. Verified editor metadata - types, lookups, limits, relations (cross-check only).
4. Legacy editors and DTOs - names and grouping only.
5. Data statistics - hypotheses only.

Every field entry carries a confidence label: `source`, `comment`, `metadata`, `inferred`,
or `unknown`. When the source is unclear, the entry says so instead of guessing.

See `SOURCES.md` for source types, evidence order and confidence rules.

`INDEX.md` and `COVERAGE.md` are generated by `util-scripts/help-check.ps1 -Write`; do not
edit them by hand.

`REFERENCE-MAP.md` is generated by `util-scripts/help-crossrefs.ps1 -Write` from the links in
the table documents. Add or fix the link in the source document, then regenerate; `-Check`
verifies that the committed map is current.

## Embedded application data

The application reads `src/XmlEditorReloaded.Data/Help/help.json`, which is generated from the
Markdown documents and embedded into `XmlEditorReloaded.Data`. Regenerate it after changing a
front matter block, a field entry, a cross-document link, or a top-level page such as
`GLOSSARY.md`/`INDEX.md`:

```sh
dotnet run --project tools/XmlEditorReloaded.HelpTool -- --source help/tables
```

The tool is deterministic: it sorts documents, table aliases, and standalone pages; writes
UTF-8 without a BOM; and uses LF line endings. Verify the committed file without rewriting it:

```sh
dotnet run --project tools/XmlEditorReloaded.HelpTool -- --source help/tables --check
```

`ITableHelpProvider` in Core resolves a dotted table name (including aliases and backup copies)
to a `TableHelp`; field lookups accept either the full path or a unique leaf name. Standalone
pages are returned by `GetDocument` and power **Help > Glossary** and **Help > Index**. The
generated data is validated by `XmlEditorReloaded.Data.Tests`, including document, table,
unique-field, and page counts. The application project fails the build with an explicit message
when `Help/help.json` is missing; the generator project stays buildable so the file can be
regenerated from the Markdown sources.

## Document format

Each table document starts with YAML front matter:

```yaml
---
schema: 1
lang: en
family: items-weapons
title: "Weapons - weapons"
tables:
  - Weapons
table_ids:
  - Items.Weapons
files:
  - Items/Weapons.xml
root: WEAPONLIST
record: WEAPON
key: uiIndex
sources:
  - Game code (item loader)
  - Item table data
status: draft
updated: 2026-11-07
---
```

The front-matter `table_ids` list keeps the canonical catalog ID (`Items.Weapons`) because the
tooling matches tables by that ID. The visible `tables` list and everything rendered in the
body use the clean name: `Weapons` for the table, `Weapons.ubWeaponClass` for a field. A dot
means "field of this table"; it never means a folder in the visible documentation.

The body has these sections, in this order:

1. `# Title`
2. `## Contents` (generated)
3. `## Purpose`
4. `## Tables` (file variants and notes)
5. `## Structure` (root, record, key, nesting, special syntax)
6. `## Fields`
7. `## Relations`
8. `## Localization`
9. `## Versions`
10. `## Sources`
11. `## Open questions`

### Structure and field order

`## Structure` is the canonical field order for the document. It must contain a fenced
hierarchy rooted at the table root and record, list every documented field exactly once, and
use the same depth-first order as the `## Fields` blocks.

The key field is always first in both places. When the key is composite, list its parts in
front-matter order before every non-key field. A table without a stable key uses `key: none`
and documents that fact in `## Structure`; it has no key field to move.

`help-check` compares the tree's field leaves with the `## Fields` order and rejects a missing,
duplicated or reordered field, as well as a key that is not first.

### Numeric fields

A measurable `Integer`, `Decimal`, `Float`, `UINT8` or `Flags` field has its numeric meaning
in a **separate bullet**, immediately after `Description` (and after `Only used with`, when
present):

```markdown
- **Description:** Item coolness: how early the item appears in enemy loadouts and shops.
- **Numeric semantics:** Higher values appear earlier; negative values are not meaningful.
```

The `Numeric semantics` bullet says what a larger value means relative to a smaller one, what
a smaller value means, and what negative values mean. Do **not** repeat that direction in
`Description`. A concrete example such as `100` = normal or `-600` = -6 HP/hour may stay in
either line when it helps understanding, but the general more/less rule belongs only in
`Numeric semantics`.

Do **not** add `Numeric semantics` to identifiers, indexes, references, enum/class codes or
0/1 switches. Those values have no more/less meaning; they are normally non-negative, and a
documented sentinel belongs in `Values`. Booleans and strings are exempt.

If the direction or negative-value meaning cannot be verified, write `Numeric semantics: Not
confirmed; see Open questions.` and add the field to `## Open questions`.

### Descriptions

`Description` explains what the field is and what it affects. Keep it free of repeated
more/less rules and of blanket disclaimers. Use the form "It is X, not Y" only when the field
can be confused with another field in the same table, or when its type and name genuinely do
not make the meaning clear. For example, `ubAssignmentType` is simply "assignment type
identifier"; it does not need "not a quantity". A field such as `ubDetectEnemiesImmediate` may
keep a disambiguation because an integer could plausibly mean enemy count, radius or a switch.

### UI locations

Do not claim that a field is shown "where the UI has room" or on a specific screen unless the
location is verified from code or a screenshot. If the exact surface is unknown, describe the
field neutrally and add the question to `## Open questions`.

A field is a level-3 heading with its full path from the document root, followed by a list:

```markdown
### `ITEMLIST/ITEM/ubCoolness`

- **Type:** `Integer` (`UINT8`)
- **Description:** Item coolness: how early the item appears in enemy loadouts and shops.
- **Values:** `0..255`; the code stores this field as `UINT8`.
- **Default:** `0`
- **Source:** game code (item loader); item table data.
- **Confidence:** `source`
```

Required keys: `Type`, `Description`, `Source`, `Confidence`. Optional: `Values`, `Default`,
`Translatable`, `Repeatable`, `Sparse`.

Do not document row counts or ranges observed in the shipped data. `Values` records only
limits enforced by code or by the field type, including metadata validation limits that mirror
code, or a list of values taken from a lookup/source definition. A range seen in one data set
is not a contract and must not be presented as one.

If a field is read only while a game option is active, add a separate line immediately
after `Description`:

`- **Only used with:** <option>`

Combine several options with commas, for example `Only used with: NCTH, NIV`. Leave ungated
fields unchanged.

A family document may set `path_mode: relative` in the front matter. Then field headings are
leaf names (`id`, `name`) and each must match the ending of a real path in every listed table.
Use this only when the table has no nested containers with the same leaf name.

### Anchors

Heading anchors follow the GitHub-style slug: lower case, punctuation and backticks removed,
underscores preserved, spaces replaced with `-`. A field heading
`### \`ITEMLIST/ITEM/ubCoolness\`` becomes `#itemlistitemubcoolness`; a path with
`CITY_INFO` becomes `#city_info...`.

Cross-document links are relative: use the target document path and, when needed, an anchor
such as `tables/Lookup.md` plus `#itemclass`.

**Preview limitation.** The DSH document preview renders headings without `id` attributes, so
same-page anchor clicks do nothing there. The links are valid in GitHub, VS Code and other
standard Markdown viewers, and they will be used by the app's own help window. This is a
preview-renderer limitation, not a document defect. `help-check` still validates every anchor
against the GitHub-style slug.

## Statuses

- `draft` - written, not reviewed; may contain open questions.
- `reviewed` - checked against the source by the author and one reviewer.
- `verified` - both the field set and the source evidence were rechecked at the end of a
  block; release documents must be at least `reviewed`, and `help-check -Release` requires
  `reviewed` or `verified`.

## Lookup and trader decisions

- **Lookups are one document.** All lookup files have the same schema (`id`, `name`); they are
  either flag/bitmask dictionaries or sequential value lists. One `Lookup.md` with per-lookup
  sections keeps the shared rules in one place. B0 analysis found no reason to split it; the
  decision is recorded here and in `COVERAGE.md`.
- **All traders are one document.** `Merchants` and the dealer inventory files are covered by
  `tables/Traders.md`; the document has two structure sections and one file-to-dealer table.

## Adding a document

1. Copy the closest existing document and change the front matter.
2. Run `pwsh -NoProfile -ExecutionPolicy Bypass -File util-scripts/help-inventory.ps1` and
   look up the table in `.tmp/help/inventory.csv`.
3. Find the loader for its root/record tag in the game source.
4. Document every field path, including nested and empty optional elements.
5. Add the document to `INDEX.md`/`COVERAGE.md` with
   `pwsh -NoProfile -ExecutionPolicy Bypass -File util-scripts/help-check.ps1 -Write`.
6. A block is done only when `help-check.ps1` reports no errors for it and the review is
   recorded in `COVERAGE.md` or the commit message.

## Checks

```powershell
# Inventory of all base tables (read-only)
pwsh -NoProfile -ExecutionPolicy Bypass -File util-scripts/help-inventory.ps1

# Validate documented tables, links and field coverage; rebuild INDEX/COVERAGE/Contents
pwsh -NoProfile -ExecutionPolicy Bypass -File util-scripts/help-check.ps1 -Write

# Release gate: all tables and fields, no drafts
pwsh -NoProfile -ExecutionPolicy Bypass -File util-scripts/help-check.ps1 -Release
```

`help-check` validates every table that is listed in a document. Tables without a document
are reported as pending; only `-Release` turns pending tables into an error. This makes a
partial block (such as B0) reviewable without pretending that the whole dataset is covered.

## Rules

- Do not modify anything under `References/`; the tools only read it.
- Do not copy record-level comments (for example the comment blocks in `Attachments.xml`)
  into field descriptions; use them only as evidence for the field meaning.
- Do not document a field from its name alone when a loader exists.
- Keep field identifiers, table names and XML element names in their original case.
- A broken source file is a finding: describe the defect and use the valid version; never
  "fix" the game data.
