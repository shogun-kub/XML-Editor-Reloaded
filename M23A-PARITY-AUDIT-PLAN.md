# M23a — аудит паритета legacy: план и протокол

**Статус:** план принят 2026-10-24; M23a0–M23a4 выполнены, дальше M23a5–M23a7.
**Основание:** `PLAN.md`, раздел M23a. Аудит выполняется заново после M22c, потому что составные ключи восьми таблиц изменили поведение item workspace и валидации.
**Результат:** `LEGACY-PARITY-REPORT.md` — матрица «функция legacy → реализация / superseded / исключено / пробел» с файлами-доказательствами и реестром пробелов для M23b. Поведение редактора в M23a не меняется.

## 1. Рамки

Эталон — `References/xml-editor` (VB.NET/WinForms). `References/JA_2_1.13_TableData_Editor` эталоном не считается. `References/Ja 2 1.13 source` в M23a не используется: для аудита достаточно legacy-редактора и данных v4/v5.

Критерий строки матрицы — фактическое поведение кода, а не пункт меню. Legacy-функция получает вердикт:

| Вердикт | Значение |
|---|---|
| `реализовано` | Поведение доступно в rewrite и покрывает существо legacy-функции. Доказательство — достижимый путь в коде, тест только подтверждает. |
| `superseded` | Legacy-поведение заменено более безопасным или более общим эквивалентом; отличие описано. |
| `исключено` | Мёртвая/скрытая функция, деструктивное поведение или осознанно вынесенный за паритет пункт (`PLAN.md`). Нужна причина и доказательство. |
| `пробел` | Функция реальна, достижима и в rewrite отсутствует или неполна. Идёт в реестр пробелов M23b. |

Bug-for-bug совместимость не требуется. Деструктивные эффекты legacy (потеря unknown-тегов, каскадное удаление без предупреждения, перезапись `ubClassIndex`, сброс отсутствующих изображений в `0/0`) не воспроизводятся и помечаются `исключено` со ссылкой на раздел «Вне паритета» в `PLAN.md`.

## 2. Почему подшаги и субагенты

Объём legacy: ~10,8 тыс. строк обычного VB-кода и ~26 тыс. строк designer-файлов; плюс ~190 файлов rewrite. Один контекст 256K этого не выдерживает, если читать обе стороны целиком.

Правила протокола:

1. **Один агент — одна функциональная область.** Вход агента — не более ~3 тыс. строк legacy и целевые файлы rewrite, найденные grep'ом, а не весь проект.
2. **Основная сессия не читает legacy массово.** Она получает от агента только финальное сообщение (≤ 25 строк) и пишет/читает файлы-секции скриптом, а не через контекст.
3. **Файл-секция — единственный носитель деталей.** Сообщение агента содержит только счётчики, список пробелов и путь к секции. Всё, что не попало в файл, для аудита потеряно.
4. **Механическая проверка вместо доверия.** Каждая строка обязана иметь `file:line` с обеих сторон; консолидация проверяет покрытие ID и наличие доказательств скриптом. Выборочно проверяются 2–3 строки каждой секции.
5. **Извлечение сначала скриптом, чтение — выборочно.** Списки меню, обработчиков, таблиц, колонок и связей извлекаются grep/awk/Python; полному чтению подлежат только файлы поведения.

Размер подшага подобран так, чтобы агент укладывался в собственное окно с запасом на запись секции.

### M23a0 — инвентаризация

Агент A (UI):

- полностью читает `GUI/App Forms/MainForm.vb`, все файлы `GUI/Forms/*.vb`, `GUI/Grid Forms/*.vb`, `BaseDataForm.vb`, `Main.vb`, `ApplicationEvents.vb`, `SettingsUtility.vb`, `IniFile.vb`;
- из `ItemDataForm.vb`, `MercGearDataForm.vb` и их designer-файлов берёт только списки обработчиков и контролов (grep), без полного чтения;
- извлекает меню, toolbar, status bar, горячие клавиши, включая `Visible = False`/`Enabled = False` и пункты без обработчика;
- присваивает ID `L-<AREA>-###` с префиксом области (`SHELL`, `GRID`, `ITEM`, `MERC`, `AUX`, `SET`, `MISC`).

Второй проход M23a0 разбит на два небольших агента, потому что полный инвентарь UI уже записан, но не был самопроверен:

- проверка меню и target appendix (`00-inventory-ui-verification.md`): 183 пункта, скрытые/мёртвые, 112 целей;
- карта полей `ItemDataForm` (`00-inventory-ui-item-fields.md`): 354 `Tag`-привязки, 107 флагов (`L-IFLAG`), 16 счётчиков (`L-ICOUNT`), lookup/image-контролы, аномалии.

Агент B (таблицы):

- скриптом извлекает из `DatabaseCode.vb` список `Make*Table`, первичные ключи (`AddConstraint`), `MakeRelation`, особые конструкторы колонок; полному чтению подлежат только нестандартные фрагменты;
- скриптом собирает из seed-миграций rewrite список таблиц, ключей, `ColumnHints`, relations и языков;
- строит матрицу «legacy-таблица → таблица rewrite → статус покрытия (`mapped`/`unmapped`/`absent`)»; для `absent` фиксирует причину;
- отмечает специальные классы (`ItemTable`, `ControlTable`, `MercStartingGearTable` и т. п.) и подшаг, где они аудируются.

Выход M23a0: каждый пункт меню и каждый обработчик имеет ID; все legacy-таблицы перечислены; неизвестных статусов покрытия не осталось; скелет отчёта содержит легенду, метод и список секций. Коммит: `M23a0: legacy feature inventory`.

### M23a1–M23a5 — секции

Каждый агент:

1. Читает свою секцию инвентаря и назначает строки матрицы существующим ID; новую функцию, которой нет в инвентаре, добавляет с ID-суффиксом и выносит в «дельта инвентаря».
2. Проверяет legacy-поведение по коду, а не по подписям меню.
3. Ищет реализацию в rewrite по ключевым словам, типам, командам и тестам; цитирует достижимый путь (`file:line`), а не только имя файла.
4. Оформляет секцию по шаблону из раздела 4 и возвращает только сводку.

### M23a6 — консолидация

- Сборка финального отчёта из секций в порядке `00 → 10 → 20 → 21 → 30 → 40 → 41`.
- Скриптовая проверка: каждый ID инвентаря встречается в матрице ровно один раз; каждая строка имеет вердикт и legacy-доказательство; `пробел` имеет поле «где должно быть».
- Дедупликация пересечений (например, shell и backend описывают одно и то же сохранение): остаётся одна строка, вторая ссылается на неё.
- Реестр пробелов: ID, область, серьёзность, предполагаемый файл/слой, предлагаемый подшаг M23b.
- Выборочная проверка 2–3 строк каждой секции по исходникам.

Коммит: `M23a: legacy parity audit`.

### M23a7 — проверка

Запускаются существующие гейты, поведение не меняется:

- `dotnet build … -warnaserror`, `dotnet test …`;
- corpus v4/v5, compare v4↔v5, copy v4→v5, perf;
- приёмка M22c: item 12 показывает 27 вложений; duplicate-baseline v5 — 2 группы `Attachments` и 1 дилер.

Ручной UI-smoke (item/merc workspace, shopkeeper, pickers, copy, фильтры, изображения, локализация, настройки, close, external-change) выполняется пользователем по чек-листу; агент не может подтвердить WPF-поведение. Результаты и дата фиксируются в отчёте. Коммит: `M23a7: parity audit verification`.

## 4. Секция и строки матрицы

Шаблон файла-секции:

```markdown
# <Подшаг> — <область>

**Дата:** …
**Legacy-файлы:** путь (строк), …
**Rewrite-файлы:** путь (строк), …
**Метод:** что прочитано полностью, что извлечено grep/скриптом.

## Сводка
| Вердикт | Кол-во |
|---|---|
| реализовано | … |
| superseded | … |
| исключено | … |
| пробел | … |

## Пробелы
| ID | Серьёзность | Суть | Где должно быть |

## Матрица
| ID | Legacy-функция | Legacy-доказательство | Реализация | Rewrite-доказательство | Вердикт | Примечание |
|---|---|---|---|---|---|---|

## Дельта инвентаря
| Новый ID | Почему не попал в инвентарь |

## Открытые вопросы
```

Требования к строке:

- ID — из инвентаря; для группового пункта (например, «открыть таблицу X») допускается одна строка с перечислением legacy-таблиц в примечании, но каждая legacy-таблица обязана быть в инвентаре.
- Legacy-доказательство — `References/xml-editor/...:line`; для «мёртвой» функции дополнительно обработчик/его отсутствие.
- Rewrite-доказательство — `xml-editor-reloaded/src/...:line` или `tests/...:line`; для `пробел` — `нет`.
- `реализовано` без цитаты кода не принимается; тест без кода — недостаточное доказательство.
- `исключено` требует причины: мёртвый код, скрытый пункт, деструктивность, вынесено в M24–M27.
- Непроверяемое утверждение идёт в «Открытые вопросы», а не в вердикт.

## 5. Бриф субагента

Каждый бриф содержит:

1. Роль и область, входные файлы с точными путями.
2. Запреты: не менять `References/` и код rewrite; не собирать решение; не делать git-коммит; писать только свой файл-секцию.
3. Требование к доказательствам и шаблон секции.
4. Разрешённые инструменты для извлечения (grep/awk/Python) и указание читать выборочно.
5. Формат ответа: ≤ 25 строк — счётчики по вердиктам, ID пробелов с одной строкой сути, путь к секции, открытые вопросы, всё остальное — только в файл.
6. Напоминание: русский текст, английские идентификаторы; UTF-8 без BOM.

## 6. Проверка M23a

1. Сборка и тесты без изменений: `dotnet build … -warnaserror`, `dotnet test …`.
2. Corpus v4 и v5, compare, copy, perf — как в `PLAN.md`.
3. item 12: 27 вложений; baseline дубликатов не изменился.
4. Скриптовая целостность отчёта: покрытие ID, наличие доказательств, отсутствие строк без вердикта.
5. `References/` не изменён; в git только документы M23a.
6. Ручной чек-лист подписан пользователем; его результат внесён в отчёт.

## 7. Риски

- **Галлюцинация агента:** строка «реализовано» без `file:line` отбрасывается; консолидация выборочно перепроверяет секции.
- **Пропущенная скрытая функция:** инвентарь включает `Visible = False`, `Enabled = False`, пустые обработчики и пункты без обработчика; designer-файлы просматриваются grep'ом.
- **Потеря деталей при передаче:** детали существуют только в файле-секции, сообщение агента — лишь сводка.
- **Расползание области:** M23a ничего не исправляет; найденные пробелы попадают в реестр M23b, крупные — в отдельный подшаг после согласования.
- **Ручная проверка:** WPF-поведение не автоматизируется в этом окружении; без подписанного чек-листа M23a не считается закрытым.
