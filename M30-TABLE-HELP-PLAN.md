# M30–M32 — документация полей TableData и контекстная справка (план)

**Статус:** plan-only, 2026-11-07. Решения D1–D4 подтверждены пользователем 2026-11-07;
ничего из описанного ещё не реализовано. Документ фиксирует объём, решения, порядок работ
и проверки; реализация — следующий шаг (раздел 14).

**Связанные документы:** `AGENTS.md` (правила), `PLAN.md` (roadmap), `PROJECT-STRUCTURE.md`
(структура), `memory/ja2-editor-metadata.md`, `M23A-PARITY/00-inventory-tables.md`.

## 1. Цель

Дать пользователю редактора ответ на вопрос «что означает это поле и что с ним можно
делать» без чтения C++-исходников игры. Работа делится на три этапа.

### 1.1. Результат A — набор справки (M30)

Отдельная папка `help/` с документами по всем базовым XML-таблицам `TableData`.
**Язык M30 — полностью английский**: термины берутся из C++/XML, чтобы не терять смысл
при переводе. Русская версия — отдельный этап M32.

- структура каждой таблицы: корень, запись, ключ, вложенные контейнеры;
- все поля, включая вложенные пути, с типом, смыслом, допустимыми значениями,
  диапазоном/единицами, значением по умолчанию и ссылкой на исходник;
- связи между таблицами и справочниками;
- отличия v4/v5 и особенности локализации;
- оглавление в каждом документе;
- явно помеченные неизвестные и открытые вопросы, без выдуманных описаний.

### 1.2. Результат B — контекстная справка в приложении (M31)

Отдельный шаг после M30: справка в приложении по активной таблице и выбранному полю.
Нужны **оба** способа доступа, а не один вместо другого.

- немодальное окно справки по `F1` для текущей таблицы;
- описание поля в тултипе заголовка колонки и в панели деталей;
- поиск по справке, переходы по связям;
- те же тексты, что в `help/`, без второй рукописной копии.

### 1.3. Результат C — русская версия (M32)

После ревью английских документов — русский перевод в `help/ru/` с теми же путями,
якорями и английскими идентификаторами полей. Перевод опирается на `GLOSSARY.md`,
чтобы один термин не переводился по-разному (пример: `Launchables` → «Боеприпасы»,
а не «Запускаемые предметы»).

### 1.4. Критерии готовности этапов

1. Все 239 базовых таблиц v5 (и 238 v4) присутствуют в `help/INDEX.md` и покрыты
   документом семейства.
2. Каждый листовой путь поля, встречающийся в v4 или v5, имеет запись в справке.
3. У каждой записи есть тип, описание и источник либо явная пометка `inferred`/`unknown`.
4. Внутренние ссылки разрешаются, формат проверяется скриптом, отчёт `COVERAGE.md`
   генерируется и показывает 100 % покрытия.
5. Пилотный блок и выборочные блоки приняты пользователем.
6. Документы написаны по-английски; русский перевод в M30 не входит.

M31 считается готовым, когда `F1`, тултипы и переходы работают на опубликованной сборке,
а тест покрытия не пропускает таблицу или поле без справки.

M32 считается готовым, когда все английские документы переведены, структура и якоря
совпадают, глоссарий соблюдён, а существующие русские строки UI приведены к нему.

## 2. Исходные данные

Замеры сделаны по `References/JA 2 1.13 v4` и `v5` (только чтение); оверлеи
`Russian.*` в счёт таблиц не входят. «Поле» — листовой элемент с непустым текстом;
контейнеры (`CITYLIST`, `ASSIGNMENT`, `MORALE`) описываются как структура.

| Показатель | Значение |
|---|---:|
| Базовых XML-таблиц в v5 | 239 |
| Базовых XML-таблиц в v4 | 238 |
| Оверлеев в v4 | 25 (`Russian.*`) |
| Листовых вхождений полей в v5 (с клонами) | 2979 |
| Уникальных листовых путей в v5 | 1646 |
| Структурных семейств (одинаковый набор путей) | 117 |
| Отличий набора полей между v4 и v5 | нет; 1 файл только в v5; `AttachmentPoint` исправлен 2026-11-07 |
| Таблиц в метабазе | 173 (66 таблиц без метаданных) |
| `ColumnHints` / `TableRelations` | 1981 / 1042 |
| Заполненных `TooltipKey` | 0 (тултип сейчас = имя поля) |
| XML-файлов с комментариями | 107, ≈325 тыс. символов |
| C++-файлов `.cpp/.h/.hpp` | 1327, 35,5 МБ |
| Таблиц, чей root/record найден в C++ по строковому литералу | 221 из 239 |

`help-inventory.ps1` считает листья по каждому файлу и включает пустые элементы (например,
`Cities.szIconFile`), поэтому его сумма — 2985 путей, а не 2979 непустых. Для покрытия важны
оба случая: пустой необязательный элемент — тоже поле таблицы.

Важные следствия:

- **Структура v4 и v5 практически одинакова.** Различаются только данные и
  `Email/EmailSenderNameList.xml`, которого нет в v4. `Lookup/AttachmentPoint.xml` был
  повреждён в v5 (лишний `</AttachmentPoint>`) и исправлен пользователем 2026-11-07; его
  восемь значений совпадают с v4. Документируем структуру один раз, различия — в разделе
  `Versions`.
- **Метаданные покрывают не всё.** 66 таблиц (армия, карта, профили солдат, часть
  laptop-таблиц и backup-копии) не имеют строки в `Tables`; справка не может опираться
  только на SQLite.
- **Комментарии в XML — сильный, но неполный источник.** 107 файлов содержат
  комментарии; местами это готовые описания полей и перечислений (`Map/Cities.xml`,
  `DifficultySettings.xml`, `MercProfiles.xml`), местами — комментарии к конкретным
  записям (`Items/Attachments.xml`, 6 тыс. комментариев), а не к схеме.
- **Загрузчики находятся.** Для всех не-lookup таблиц root/record встречается в C++;
  имена файлов — `XML_*.cpp`, но часть загрузчиков живёт в игровых файлах
  (`Tactical/Weapons.cpp`, `Strategic/strategicmap.cpp`).
- **Справки в приложении нет.** `TableColumnViewModel.Tooltip` возвращает
  `TooltipKey ?? XmlFieldName`, а `TooltipKey` нигде не заполнен.

## 3. Границы

### Входит в M30

- базовые таблицы v4/v5 (объединение), включая таблицы без метаданных и исправленный lookup;
- все листовые поля, включая вложенные пути и повторяющиеся контейнеры;
- смысл, тип, диапазоны, единицы, значения по умолчанию, перечисления, ссылки;
- связи: lookup-поля, внешние ключи, родственные таблицы;
- локализация: какие поля переводятся, как устроен оверлей;
- источники: файл и строка C++, XML-комментарии, метаданные.

### Не входит в M30

- изменение игровых данных и `References/` (только чтение);
- добавление недостающих метаданных в SQLite (отдельная задача; справка лишь фиксирует пробелы);
- русский перевод документов — отдельный этап M32, не M30 (см. D2);
- UI-код справки (M31);
- описание каждой записи таблицы (например, всех 6 тыс. строк `Attachments.xml`);
- генерация XSD/валидаторов.

## 4. Ключевые решения

### D1. Единица документирования — семейство, а не файл

239 файлов сводятся к 117 структурным семействам; после объединения торговцев и
предварительного объединения lookup-таблиц остаётся **≈94 документа**. Один документ
описывает структуру и поля один раз, а в разделе «Tables» перечисляет все файлы-алиасы.
Каждый документ начинается с оглавления (см. 6.5).

Причины: 80 инвентарей дилеров имеют одинаковые 3 поля, 20 таблиц выбора — 53 поля;
239 отдельных документов дали бы ≈1300 повторяющихся записей и рассинхронизацию.

Каждая из 239 таблиц всё равно получает строку в `INDEX.md` и сопоставление с документом
и разделом; приложение сможет открыть справку для любой таблицы. Если у таблицы внутри
семейства другая семантика (например, `GunChoices_Enemy_*` vs `GunChoices_Militia_*`),
в документе появляется отдельный подраздел «Variants», но не копия полей.

Два уточнения по решению пользователя:

- **Все торговцы — один документ.** `NPCInventory.Merchants` (20 полей) и 80 файлов
  инвентарей дилеров (3 поля) входят в `tables/Traders.md`; у них два раздела структуры,
  но общее оглавление и общие ссылки.
- **Lookup-таблицы пока предварительно один документ.** В B0 делается отдельный анализ
  (id/name, flag vs sequence, значения, ссылки в коде); после него решается, оставить
  один `Lookup.md` с разделами или разделить по видам. Итоговое число документов может
  вырасти на 0–3.

### D2. Язык: сначала полностью английский, русский — отдельным этапом

**M30 — только английский.** Термины берутся из C++/XML и комментариев игры; это
устраняет цепочку «английский → русский → английский» и потерю смысла. Имена полей,
таблиц, типов и файлов — всегда как в игре.

**M32 — русская версия** в `help/ru/` с теми же путями, якорями и английскими
идентификаторами. Английские документы остаются каноном; русские не смешиваются с ними
в одном файле. Перевод начинается только после ревью английского оригинала.

**`GLOSSARY.md` — обязательный словарь.** Для каждого термина: английский канон,
утверждённый русский перевод, запрещённые варианты, контекст. Пример из решения
пользователя:

| English | Russian (approved) | Forbidden / notes |
|---|---|---|
| Launchables | Боеприпасы | «Запускаемые предметы», «запускаемое» |
| ... | ... | ... |

`Launchables` → **«Боеприпасы»**, а не «Запускаемые предметы».

В текущем `Strings.ru.resx` уже есть расхождение: `ItemSection.Items_Launchables` =
«Запускаемые предметы» (строка 1098), а `ItemSectionReverse.Items_Launchables` =
«Боеприпасы» (строка 1113). M32 приводит такие строки к глоссарию; это отдельная
проверка, а не побочный эффект перевода.

Если термин встречается впервые — сначала строка в `GLOSSARY.md`, потом использование
в документе. Это же правило действует для UI-строк приложения.

### D3. Иерархия источников и достоверность

1. **Код загрузчика/сохранения игры** — поведение, типы, значения по умолчанию,
   ограничения. Главный источник.
2. **Комментарии в XML и readme** — замысел автора, перечисления, диапазоны. Проверять
   по коду; комментарии бывают устаревшими.
3. **Проверенные метаданные редактора** — тип, lookup, границы, связи. Использовать как
   перекрёстную проверку, не как единственный источник.
4. **Legacy-редакторы и DTO** — только имена, группировка, подсказки.
5. **Статистика данных** — частоты, диапазоны, пустые значения. Только для гипотез.

Каждая запись поля получает `confidence`:

| Метка | Значение |
|---|---|
| `source` | подтверждено кодом загрузчика/сохранения |
| `comment` | взято из комментария XML/readme, код не проверен |
| `metadata` | взято из проверенных метаданных |
| `inferred` | выведено по имени/данным, требует проверки |
| `unknown` | назначение не установлено; описание честно говорит об этом |

Правило: **не придумывать смысл**. Лучше `unknown` с вопросом, чем правдоподобная догадка.
Номер строки в ссылке — ориентир: при изменении исходников важнее имя функции и тег,
поэтому в «Источниках» указываются и функция, и тег.

Термины — по `GLOSSARY.md`: новый термин сначала попадает в словарь (английский канон +
утверждённый русский перевод), затем используется в документах и UI.

### D4. Документы — источник истины, формат — строгий Markdown

`help/**/*.md` — единственная рукописная копия. `INDEX.md` и `COVERAGE.md` генерируются.
M31 получает данные из этих же документов через генератор, а не из второй рукописной
таблицы. Формат фиксирован (раздел 6) и проверяется скриптом.

### D5. Размещение и именование

├── tables/
│   ├── Lookup.md
│   ├── Traders.md
│   ├── Items/

Папки повторяют `TableData`, но имена файлов — по семейству, а не по каждому XML.
Точки-имена таблиц с пробелами (`Inventory.Backup original Gun Choices.…`) в front
matter и `INDEX.md` сохраняются дословно; имена файлов справки — короткие slug'и.
Ссылки между документами — относительные, от `tables/`. Исходники игры не цитируются
файлами и строками: `Source` — общая категория (`game code`, `table data`, `metadata`),
чтобы документы не ломались при публикации без `References/` и не устаревали от
перемещения строк.

### D6. Клоны, backup-папки и повреждённые файлы

- `Inventory/Backup original Gun Choices/*` — backup-копия без отдельной игровой
  семантики; строка-алиас в документе выбора.
- **Все торговцы — `Traders.md`.** `NPCInventory.Merchants` и 80 инвентарей дилеров
  описаны в одном документе: два раздела структуры, одна таблица соответствия
  «файл → дилер», общие поля и ссылки. Источники — `XML_Merchants.cpp` и загрузчик
  инвентарей дилеров (`Arms Dealer Init.cpp` / `XML_TonyInventory.cpp`).
- **Lookup — после анализа.** 23 lookup-таблицы предварительно идут одним `Lookup.md`
  с разделами; B0 анализирует вид (последовательный / flag / список выбора) и решает,
  не разделить ли документ. `Lookup/AttachmentPoint.xml` (v5) был повреждён и
  исправлен пользователем 2026-11-07; fallback на v4 остаётся страховкой для будущих
  повреждений.
- `AltSectors.xml`, `CoolnessBySector.xml`, `Sounds.xml`, `BurstSounds.xml` — особые
  таблицы без обычных записей; для них отдельные разделы «формат строки/матрицы».

### D7. M31: генерация данных, без новой миграции SQLite (первая версия)

Документы → `HelpTool` (консольный инструмент) → `HelpData.json` → встроенный ресурс
приложения. Метаданные SQLite остаются источником типов/lookup/связей, а справка —
контентом. Так избегаем миграции на тысячи строк и ручной синхронизации.

Если позже понадобится редактирование справки без пересборки — можно добавить таблицы
`TableHelp`/`FieldHelp`; текущий формат документов это не блокирует.

### D8. M31: и окно справки, и тултипы

- Немодальное окно `HelpWindow` по `F1` для активной таблицы.
- `F1` сейчас занят окном About (`ShortcutCatalog`): в M31 `F1` становится контекстной
  справкой, About остаётся в меню без горячей клавиши. Это изменение горячей
  клавиши нужно отразить в `USER-GUIDE` и UI-smoke S81.
- Разделы: обзор, поля (с фильтром), связи, локализация, источники.
- Переход по связи открывает таблицу в основном окне.
- Тултип заголовка колонки и кнопка «?» в панели деталей показывают краткое описание —
  это дополнение к окну, а не замена.
- Меню `Справка`: «Справка по таблице», «Глоссарий», «Индекс таблиц», «О программе».
- UI-строки — RESX (EN/RU); текст справки — язык документа (EN до M32).

## 6. Формат документа

### 6.1. Front matter

```yaml
---
schema: 1
lang: en
family: items-weapons
title: "Items.Weapons — weapons"
tables:
  - Weapons
table_ids:
  - Items.Weapons
files:
  - Items/Weapons.xml
root: WEAPONLIST
record: WEAPON
key: uiIndex
sources:
  - Game code (item loader)
  - Item table data
status: draft          # draft | reviewed | verified
updated: 2026-11-07
---
```

`tables` — чистые имена для чтения; `table_ids` — точные точки-имена из каталога для
`help-check`; `files` — пути относительно `TableData`. `key` может быть пустым, если ключ
составной или не определён; тогда это описывается в разделе `Structure`. В `help/ru/` те же
ключи, но `lang: ru` и переведённые `title`.

### 6.2. Обязательные разделы (английские заголовки)

1. `# Title` — человекочитаемое имя таблицы.
2. `## Contents` — оглавление (6.5).
3. `## Purpose` — 1–3 абзаца: что таблица задаёт и кто её читает.
4. `## Tables` — таблица вариантов: файл, root/record, записей, примечание.
5. `## Structure` — иерархия, контейнеры, ключ, повторяемость, особые форматы.
6. `## Fields` — записи полей (6.3).
7. `## Relations` — ссылки на lookup/таблицы с смыслом связи.
8. `## Localization` — переводимые поля, оверлей, ограничения длины.
9. `## Versions` — отличия v4/v5 (если есть).
10. `## Sources` — общие категории источников: game code, table data, metadata.
11. `## Open questions` — что не удалось подтвердить; пустой раздел допустим.

### 6.3. Запись поля

Поле — заголовок `###` с полным путём от корня, затем список. Ключи английские,
как в документе:

```markdown
### `ITEMLIST/ITEM/ubCoolness`

- **Type:** `Integer` (`UINT8`)
- **Description:** item "coolness": how early it appears in enemy loadouts and shops;
  influences AI equipment selection.
- **Values:** integer 0–255; game data uses small values, 0 = earliest/cheapest.
- **Default:** `0`
- **Source:** game code (item loader); item table data.
- **Confidence:** `source`
```

Если у поля есть lookup/перечисление — ссылка в `Values` или в `Relations`.
Если поле переводимое — `Translatable: yes` и ссылка на раздел локализации.
Если поле повторяется — `Repeatable: 1..N` и описание контейнера.
Если поле встречается не во всех записях — `Sparse: <доля>`.

### 6.4. Ссылки

- Внутри справки: `[Lookup.WeaponType](../Lookup.md#lookup-weapontype)`.
- На поле: `[…](#itemlistitemubcoolness)` (якорь — путь без спецсимволов).
- На исходник: только общее описание (`game code (loader)`), без файлов и строк.
- На таблицу, у которой нет отдельного документа: ссылка на раздел семейства.

### 6.5. Оглавление

Каждый документ начинается с `## Contents`: ссылки на `Purpose`, `Tables`, `Structure`,
`Fields` (по группам), `Relations`, `Localization`, `Versions`, `Sources`,
`Open questions`. Для больших документов (`Items.Items`, `MercProfiles`, `Backgrounds`)
оглавление дополнительно группирует поля по смыслу (General, Stats, Flags, …).

`help-check -Write` пересобирает оглавление и `INDEX.md`; ручная правка оглавления
не требуется. Битая ссылка в оглавлении — ошибка проверки.

## 7. Методика документирования

Для каждого семейства:

1. **Инвентаризация.** Скрипт собирает root, record, все листовые пути, число записей,
   присутствие полей, примеры значений, комментарии XML. Результат — JSON/CSV, не
   коммитится (или кладётся в `.tmp`).
2. **Карта источников.** По root/record находится загрузчик: строковый литерал в
   `.cpp/.h`; для таблиц без литерала — по имени файла и вызовам. Фиксируются функции
   чтения и сохранения (последняя часто даёт полный список полей и типов).
3. **Трассировка поля.** Тег → ветка `strcmp(name, "...")` → присваивание члену структуры
   → объявление в заголовке → комментарий/значение по умолчанию → использование в коде.
4. **Значения и единицы.** Перечисления, битовые маски, lookup-таблицы, диапазоны
   спиннеров, масштаб (например, вес/цена/проценты).
5. **Перекрёстная проверка.** Метаданные (тип, lookup, min/max, relation) и фактические
   данные v4/v5; расхождения фиксируются, а не сглаживаются.
6. **Запись.** Документ по шаблону, **по-английски**; ссылки; `confidence`; оглавление;
   открытые вопросы.
7. **Термины.** Новый термин — сначала строка в `GLOSSARY.md` (English canon +
   approved Russian + forbidden variants), затем использование.
8. **Самопроверка.** `help-check` по блоку; затем ревью (пилот — пользователем,
   далее выборочно).

Особые случаи:

- **Матрицы/строки.** `AltSectors` (атрибут `y`, 16 чисел в тексте), `CoolnessBySector`,
  `Sounds`/`BurstSounds` — описывать формат, а не искать «поля».
- **Lookup.** Сначала анализ: 23 таблицы, `id`/`name`, вид (последовательный / flag /
  список выбора), фактические значения, ссылки в коде. Затем решается группировка:
  один `Lookup.md` с разделами или несколько документов по видам. Для flag-lookup —
  какие биты именуются, какие комбинации допустимы.
- **Вложенные контейнеры.** Указывать путь, кратность, ключ вложенной записи, поведение
  при отсутствии.
- **Ключ не определён.** Перечислить поля-кандидаты, объяснить, почему ключ не назначен,
  и пометить `unknown`; не выдумывать ключ ради красивой таблицы.
- **Оверлеи.** В справке таблицы — только переводимые поля и правила оверлея; сами
  оверлеи — в `help/Localization.md` (один общий документ, не 25 таблиц).
- **Повреждённые файлы.** Не чинить автоматически; описать дефект и взять валидную
  версию (v4 или исправленную пользователем).

## 9. Проверки и гейты

### 9.1. `help-inventory.ps1`

Читает `TableData` v4/v5, строит:

- список базовых таблиц (без оверлеев), root/record;
- листовые пути, число записей, присутствие, примеры значений;
- комментарии XML, привязанные к полям (где можно);
- список файлов-кандидатов C++ по root/record.

Пишет JSON/CSV в `.tmp/help/` и краткую сводку в консоль. Не коммитится.

### 9.2. `help-check.ps1`

Проверяет:

1. Каждая таблица каталога есть в `INDEX.md` и в `tables` front matter ровно одного документа.
2. Каждый листовой путь v4/v5 покрыт записью поля (по полному пути); лишние записи — предупреждение.
3. Front matter: обязательные ключи, `schema: 1`, `lang: en`, корректные имена таблиц.
4. Запись поля: есть `Type`, `Description`, `Source`, `Confidence`.
5. Внутренние ссылки и якоря разрешаются; оглавление совпадает с заголовками.
6. Нет дублирующихся путей в одном документе.
7. `status` не `draft` для релизного прогона (`-Release`).
8. Нет терминов вне `GLOSSARY.md` (отчёт `-Glossary`; спорные — предупреждение).
9. Генерирует `INDEX.md`, `COVERAGE.md` и разделы `Contents` (`-Write`).

Коды выхода: 0 — чисто; 1 — пробелы/ошибки. В CI — отдельный шаг после сборки
(документы не влияют на `dotnet build`).

### 9.3. Ревью

- B0 — пользователь проверяет 2–3 документа целиком.
- Каждый блок — самопроверка автора + выборочное ревью пользователем (5–10 полей).
- B9 — сквозная проверка терминов и ссылок.

### 9.4. Защита `References/`

До и после прогонов — хеши `References/JA 2 1.13 v4` и `v5` (или `git status` для
отслеживаемых файлов); документы не пишут в `References/`.

## 10. M31 — справка в приложении

### 10.1. Данные

`HelpTool` (консольный проект или скрипт) читает `help/**/*.md` и генерирует
`help.json`:

```json
{
  "schema": 1,
  "lang": "en",
  "tables": {
    "Items.Weapons": {
      "doc": "Items/Weapons.md",
      "title": "Items.Weapons — weapons",
      "summary": "...",
      "root": "WEAPONLIST",
      "record": "WEAPON",
      "fields": {
        "WEAPONLIST/WEAPON/uiIndex": {
          "path": "WEAPONLIST/WEAPON/uiIndex",
          "type": "Integer",
          "description": "...",
          "values": "...",
          "default": "0",
          "source": "game code (weapon loader); weapon table data",
          "confidence": "source"
        }
      },
      "links": [
        { "field": "ubWeaponType", "target": "Lookup.WeaponType", "kind": "lookup" }
      ]
    }
  }
}
```

Генерация детерминированная; `help.json` встраивается в приложение как ресурс
(или генерируется в `HelpData.g.cs`). Время сборки не должно зависеть от парсинга
Markdown в рантайме. Для M32 генератор делает второй `help.ru.json` из `help/ru/`;
приложение выбирает ресурс по языку UI.

### 10.2. Контракты

В `Core`:

```csharp
public interface ITableHelpProvider
{
    TableHelp? GetTableHelp(TableName table);
    FieldHelp? GetFieldHelp(TableName table, string fieldPath);
    IReadOnlyList<HelpSearchResult> Search(string query, int limit);
}
```

Модели: `TableHelp`, `FieldHelp`, `HelpLink`, `HelpSearchResult`. Реализация — в `App`
или `Data` (зависит от способа встраивания).

### 10.3. UI

- `HelpWindow` + `HelpViewModel`: заголовок, обзор, вкладки/секции, фильтр полей,
  связи, источники. Окно и тултипы — **оба** обязательны; тултип не заменяет окно.
- `F1` в главном окне: активная таблица и `CurrentCellField` (уже есть в
  `TableEditorViewModel`). Перед этим — переназначение `F1` (сейчас About) и правка
  подсказок/руководства; About остаётся в меню без горячей клавиши.
- Тултип заголовка колонки: `TableColumnViewModel.Tooltip` берёт краткое описание
  из `ITableHelpProvider` (fallback — текущее поведение).
- Панель деталей: кнопка «?» у поля.
- Меню «Справка»: таблица, глоссарий, индекс, About.
- Переход по связи — через существующий `TableNavigationRequest`/навигацию.
- Если поле не описано — «описание не добавлено» + ссылка на `COVERAGE.md`;
  в релизе таких полей быть не должно.

### 10.4. Локализация

- Текст справки до M32 — английский; после M32 приложение выбирает `help.json` или
  `help.ru.json` по языку UI.
- Названия полей и таблиц не переводятся.

### 10.5. Тесты M31

- Покрытие: каждая таблица/поле каталога имеют справку (тот же `help-check` в CI).

## 11. M32 — русская версия

Предпосылки: английские документы M30 в статусе `reviewed`/`verified`; `GLOSSARY.md`
согласован; M31 умеет выбирать язык контента.

- `help/ru/` повторяет структуру `help/`: те же имена семейств, путей и якорей,
  те же ключи front matter, `lang: ru`; переводятся только текст и `title`.
- Английские идентификаторы полей, таблиц, типов и файлов не переводятся.
- Порядок перевода — как блоки M30 (B0 → B8); перед блоком проверяются термины.
- **Аудит существующих русских строк.** Ищутся запрещённые варианты из глоссария
  в `Strings.ru.resx`, `USER-GUIDE-RU.md` и документах; строки приводятся к
  утверждённому термину. Пример: `Launchables` — сейчас в RESX одновременно
  «Запускаемые предметы» (1098) и «Боеприпасы» (1113); утверждено — «Боеприпасы».
- `help-check -Lang ru` проверяет структурный паритет: каждый английский документ
  имеет русский, наборы полей и якорей совпадают, нет пропусков и лишних записей.
- `TRANSLATION.md` — статус по документам (draft/translated/reviewed), дата, кто проверил.
- Приложение получает `help.ru.json`; переключение языка UI меняет и справку.

Критерий готовности: 100 % документов переведены, паритет структуры и якорей,
глоссарий соблюдён, существующие русские строки UI согласованы, выборочное
двуязычное ревью пройдено.

Вне M32: повторный перевод английского канона, перевод имён полей, машинный перевод
без ревью.

## 12. Риски

| Риск | Мера |
|---|---|
| Смысл поля понят неверно | Ссылка на строку кода; `confidence`; ревью; лучше `unknown` |
| Объём и контекст | Блоки, шаблон, генератор, семейства; один блок за сессию |
| Дублирование клонов | Семейные документы; алиасы; INDEX |
| 66 таблиц без метаданных | Справка независима; ключ/тип выводятся и помечаются |
| Повреждённые данные | Документировать дефект; брать валидную версию; не править |
| Устаревшие XML-комментарии | Код приоритетнее; расхождения — в `Open questions` |
| Расхождение v4/v5 | Раздел `Versions`; проверка по обоим наборам |
| Русский перевод исказит смысл | Английский канон + `GLOSSARY.md` + двуязычное ревью |
| Русские строки уже расходятся | Аудит RESX/документов в M32 (пример `Launchables`) |
| Документы разойдутся с игрой | `help-check` в CI; версия источника в front matter |
| Ссылки на `References/` гниют | Только текстовые ссылки на исходники |
| M31 превратится в редактор справки | Фиксированный контент; редактирование — вне scope |
| UI-smoke мешает работе | Один сценарий, по правилам AGENTS |
| `F1` уже занят About | Переназначить в M31 на справку, About оставить в меню без клавиши; обновить USER-GUIDE и S81 |
